## API: Sales — contract and design decisions

Summary of the contract and design decisions for the `Sales` endpoints. This text should be included in the project README to guide the implementation of the server and clients.

### Endpoints and behaviors

- `POST /api/sales` — 201
  - Creates a new sale.
  - The server generates the `saleNumber` (unique, immutable).
  - The client provides `saleDate` (ISO UTC) and other fields in the body.
  - Returns the calculated sale object with prices, totals, and status.

- `GET /api/sales/{id}` — 200
  - Returns the sale with its items (including canceled items) and the calculated values.
  - Response uses the envelope `{ "success": true, "data": { ... } }`.

- `GET /api/sales` — 200
  - Returns a filtered and ordered page of sales.
  - Paginated response specific to sales: `{ "success": true, "data": [ ... ], "totalItems": X, "currentPage": Y, "totalPages": Z }`.

- `PUT /api/sales/{id}` — 200
  - Updates an active sale; recalculates values based on active items.
  - The body must send the header fields (same format as POST) and the complete list of desired active items.
  - Existing items have `id` (GUID). New items have `id: null`.
  - Items omitted from the active list will be marked as canceled; items already canceled remain canceled and are returned in the details.
  - Validate the entire update before modifying tracked entities; if validation fails, return 400 with reasons.
  - `saleNumber` is immutable — cannot be changed by the client.
  - Editing an already canceled sale should return 409 Conflict.

- `DELETE /api/sales/{id}` — 204
  - Removes a sale and all its item records from an operational perspective.

- `PATCH /api/sales/{id}/cancel` — 200
  - Marks the sale and its active items as canceled.
  - Preserves records (does not remove prices or history).
  - Idempotent operation: canceling again does not create duplicate events.

- `PATCH /api/sales/{saleId}/items/{itemId}/cancel` — 200
  - Marks only the item as canceled and recalculates the sale total considering only active items.
  - Preserves the item's original prices and values.

### Important rules and decisions

- **Response envelope**
  - Single resource responses: `{ "success": true, "data": { ... } }` (compatible with `ApiResponseWithData<T>` from the template).
  - Paginated listings for sales use `{ "success": true, "data": [ ... ], "totalItems": int, "currentPage": int, "totalPages": int }`.

- **Numbers, rounding, and types**
  - Monetary values use `decimal` with two decimal places.
  - Rounding: `MidpointRounding.AwayFromZero`.

- **Total calculation**
  - The client does NOT send discounts, item totals, sale total, or cancellation status — the server calculates and returns these fields.
  - `lineAmount` for each item is `quantity * unitPrice` (preserved even after cancellation).
  - `totalAmount` for the sale is the sum of `lineAmount` for active items only; if the entire sale is canceled, `totalAmount` = 0.

- **Cancellation**
  - Cancellation preserves original prices and values; it does not recreate or alter history.
  - Cancellation operations are idempotent.

- **Validation and domain rules**
  - One active line per `productId` per sale. Duplicate product lines in the create/update request are rejected with 400.
  - We follow the policy: reject duplicates rather than automatically merging them.
  - For `PUT`, validate the entire update before applying changes to the database; failures must abort without altering the state.

- **Edit and delete behavior**
  - Editing a canceled sale returns 409.
  - Deleting (`DELETE`) is a separate operation that removes the sale and its items.

### Implementation notes

- `saleNumber` is generated by the server and must be immutable.
- `saleDate` is provided by the client and must be in ISO UTC format.
- For paginated listings, adapt the response DTO to use the names `data`, `totalItems`, `currentPage`, and `totalPages` for compatibility with expected consumers.
